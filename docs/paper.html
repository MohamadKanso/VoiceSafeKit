Technical paper · v0.5

How VoiceSafeKit was built

Speech-to-text writes what people say, not what they mean. This paper explains how VoiceSafeKit reads personal data in that spoken form and keeps it away from the language model behind a voice assistant.

Mohamad Kanso November 2026 Spoken PII, Privacy and Voice Agents
Abstract

Speech-to-text engines write what people say. A card number arrives as "four two four two four two…", an email as "alex dot rivera at gmail dot com", a phone number as "oh seven seven double oh…". Text-only PII tools, regex filters and NER models alike, are built for written text and pass all three straight through to the model. VoiceSafeKit is a privacy filter that sits between speech-to-text and a large language model. It first normalises spoken forms into written ones, runs its detectors on the written form, then maps every finding back to the original words so the redaction lands on what was actually said. Version 0.5 is a Python library with zero runtime dependencies, a browser app that transcribes with Whisper on the user's device, and drop-in processors for Pipecat and LiveKit Agents. On real Whisper transcripts it protects 94% of PII utterances with no false alarms; Microsoft Presidio, run with its defaults, protects 73% and raises false alarms on 42% of ordinary requests. This paper explains the problem, the design, what it detects, how it was measured and where it still fails.

01 - The Problem

Voice assistants and the data they leak

Voice assistants are becoming more capable because they can now pass what a user says directly to a large language model. That creates a real risk. When someone speaks to an assistant, they often include private details without thinking: a card number to pay for something, an email address for a receipt, a one-time code a "bank" asked them to read out. The assistant transcribes all of it and sends it upstream.

There is usually nothing in between, and the tools that do exist were built for a different kind of text. PII filters look for 4242 4242 4242 4242 and alex.rivera@gmail.com. Speech-to-text engines often write something else:

What speech-to-text actually writes 
my card is four two four two four two four two four two four two four two four two
email me at alex dot rivera at gmail dot com
call me on oh seven seven double oh nine double oh one two three
my social is four seven one, five five, eight eight four three

A regex for card numbers needs digits. A named-entity model reads "four" as a word, not a number. Both return nothing. Before version 0.5, VoiceSafeKit had the same blind spot: every one of those lines came back SAFE.

Transcript0.4 (text-only rules)0.5 (spoken forms)
my card is four two four two …SAFE, nothing foundREVIEW: my card is [payment number removed]
email me at alex dot rivera at gmail dot comSAFE, nothing foundREDACT: email me at [email removed]
call me on oh seven seven double oh nine …SAFE, nothing foundREDACT: call me on [phone removed]
my social is four seven one, five five, …SAFE, nothing foundBLOCK: my social is [SSN removed]

VoiceSafeKit addresses that gap. It is a safety layer that reads a transcript the way speech-to-text writes it, removes the sensitive parts before they leave the device or reach the model, and can put the values back into the reply when the assistant genuinely needs to say them.

Example

A user says: "My email is john@example.com and my password is BlueFalcon2026. Help me reset my account." Without filtering, that entire string goes to the model. VoiceSafeKit returns REVIEW with a score of 53, sends "My email is [email removed] and my [secret removed]. Help me reset my account." and tells the assistant never to echo the credentials back.

02 - Architecture

Three stages: Capture, Check, Protect

The system is split into three clearly separated stages. Each one has a single responsibility. The same stages run in three places: the browser app, the Python library and the Pipecat and LiveKit processors, where the framework's own speech-to-text service does the capturing.

STAGE 01

Capture

Record audio via the browser microphone and transcribe it locally with Whisper, accept pasted text, or take the final transcript from a voice framework's STT.

STAGE 02

Check

Normalise spoken numbers and emails, run the pattern and intent rules on the written form, score the result and assign a decision.

STAGE 03

Protect

Redact the original words, or swap them for reversible placeholders, and give plain-English guidance for the assistant to follow.

In the browser, the data flow within Stage 1 is worth showing explicitly:

Nothing in that chain touches a server. The audio is captured in the browser, decoded in the browser and transcribed in the browser. The only thing that ever leaves the device is the cleaned transcript and only if the user chooses to forward it.

Stage 2 is where version 0.5 changed most. Detection runs on a written copy of the transcript, and redaction runs on the original:

03 - In-Browser Speech Recognition

Why Whisper and how it runs in a browser

The first version of VoiceSafeKit used the browser's built-in Web Speech API. It was unreliable. The API stops recognising speech after a short pause, varies widely between browsers and in some Chrome versions silently fails unless a separate microphone permission call has already been made. It is also inherently online: Chrome's implementation sends audio to Google's servers.

The replacement is Whisper, a speech recognition model published by OpenAI in 2022 and widely regarded as one of the most accurate open speech models available. The variant used here is whisper-tiny.en, an English-only model around 75 MB in size.

How it runs in the browser

Transformers.js (by Hugging Face) runs an ONNX export of the model via WebAssembly. No GPU is needed. The model downloads once and is then stored in the browser's cache. Every subsequent run is instant.

The transcription pipeline, simplified:

app.js - transcription 
// Decode the audio blob to 16kHz mono - Whisper's required format
const audioCtx = new AudioContext({ sampleRate: 16000 });
const decoded  = await audioCtx.decodeAudioData(arrayBuffer);
const float32  = decoded.getChannelData(0);

// Run Whisper
const model  = await pipeline("automatic-speech-recognition",
                              "Xenova/whisper-tiny.en");
const result = await model(float32, { sampling_rate: 16000 });
const text   = result.text.trim();

The model is loaded lazily: it starts downloading as soon as the user presses Record, so by the time they finish speaking, it is usually ready. On repeat visits, the cached version loads in under a second. The transcript then goes through the same normaliser and rules as the Python library: app.js mirrors spoken.py, rules.py and engine.py, and a spoken-mode toggle shows the difference normalisation makes.

Why tiny over base? The tiny model (75MB) completes transcription in roughly 2-4 seconds on a typical laptop. The base model (145MB) is more accurate but takes longer to load and process. For a tool where speed matters for usability, tiny is the right trade-off. The benchmark in section 16 uses base.en through faster-whisper, closer to what a server-side voice agent would run.

04 - The Detection Engine

What it looks for and how it decides

Once the transcript exists as plain text, and spoken forms have been rewritten into written ones, VoiceSafeKit runs it through a set of detection rules. Each rule has a pattern (a regular expression), a severity level, a base confidence, a human-readable explanation and a replacement string for the redacted output. Some rules mark a value group so that only the value is redacted and the context stays readable: "my pin is [PIN removed]". Several rules also run a validator before a match counts: Luhn or card context for cards, mod-97 for IBANs, issued ranges for SSNs, date and IP checks for phone numbers.

Severity and scoring

Every finding contributes to a risk score: its severity points multiplied by its confidence (section 09), summed and capped at 100.

Level Points Examples

MEDIUM 22 Email, phone, partial card, date of birth, name, street address, postcode, IP address
HIGH 36 Card number, PIN, one-time code, password, API key, medical / legal / financial intent, distress, coercion
CRITICAL 55 SSN, IBAN, CVV, passport, UK National Insurance number, emergency language

The decision is checked from the top down: a critical finding blocks regardless of score, and a high finding always asks for review.

The REDACT threshold is 17, not 22, because scores are confidence-weighted. A spoken UK mobile number is one medium finding at 85% confidence: 22 × 0.85 = 18.7, rounded to 19, which still lands in REDACT.

Overlap resolution

When two rules match overlapping text (for example, a 16-digit number that could be both a phone and a card, or a passport number that also looks like a phone), the higher-severity rule wins. Ties go to the earlier, then the longer, match. The overlapping lower-severity finding is discarded. This prevents double-counting and ensures the more serious label is shown.

app.js - overlap resolution 
function removeOverlaps(findings) {
  const accepted = [];
  const prioritySorted = [...findings].sort(
    (a, b) =>
      severityRank[b.severity] - severityRank[a.severity] ||
      a.start - b.start ||
      b.end - b.start - (a.end - a.start)
  );
  for (const finding of prioritySorted) {
    if (!accepted.some((x) => finding.start < x.end && x.start < finding.end)) {
      accepted.push(finding);
    }
  }
  return accepted.sort((a, b) => a.start - b.start);
}

Why no framework?

Using React, Vue or any other framework would require a build step, a node_modules folder and a bundler. The point of this project is that it should run as static files on any HTTPS host with no server, no backend and no deployment complexity. Vanilla HTML/JS keeps that simple. The same reasoning applies to the Python core: pip install pulls in nothing else.

06 - Design Decisions

The reasoning behind key choices

Why no API key for transcription? Any API key embedded in a public GitHub repository is public. Anyone can read your source, extract the key and use it. Running the model entirely in the browser avoids this problem entirely. It also means the audio never touches a third-party server, which is directly relevant to the privacy use case.

Why normalise first instead of writing spoken-form rules? A separate set of rules for "four two four two" would duplicate every detector and every validator. Rewriting the speech into its written form once means the Luhn check, the mod-97 check and the SSN range filter all apply to spoken numbers for free, and the same detector can be run with normalisation switched off as a baseline. Section 12 explains how it works.

Why Luhn or card context? A 13-19 digit number is flagged as a card when it passes the Luhn checksum, or when a card word (card, credit, debit, visa, mastercard, payment) sits within 32 characters of it. A Luhn-valid number also gets a small confidence boost, from 95% to 99%. Luhn alone is not enough for voice: a user dictating a card may say it with a slip, or the STT may mishear one digit. That number fails Luhn but is still the user's card, and "my card number is …" makes that clear. Context alone is not enough either, because people read card numbers without saying "card". A 16-digit reference number with neither signal is left alone, so order and tracking numbers do not trip the filter.

Why rules and not a model? A voice agent has a latency budget of a few hundred milliseconds per turn. The rules take about 0.06 ms per utterance (median on the SpokenPII set), need no download and produce exact spans that can be audited. A general NER model does not fix the core problem anyway: it reads "four" as a word. Presidio with spaCy's large English model takes about 3 ms per utterance on the same set and still misses most spoken PII (section 16).

Why zero dependencies? Voice agent stacks are already heavy. A privacy layer should be easy to read in full, easy to install anywhere and impossible to break with a dependency upgrade. Encrypted exports moved to the optional [crypto] extra in 0.5, and Pipecat and LiveKit are optional extras that only the integration modules import. CI has a job that installs the package with --no-deps and runs the tests and benchmark to keep it that way.

Why flag intent (medical, legal, financial) separately from data? A transcript might not contain any personally identifiable information but still be problematic. Someone asking an AI for a medication dose change or investment advice needs different handling to someone asking for a restaurant recommendation. Intent rules capture that distinction. When placeholders are used (section 14), intents are reported but left in the text, because the model needs them to respond well.

Why client-side everything? The thesis of the project is that sensitive voice data should not leave the device unless it has been checked and cleaned. If the checking itself required sending data to a server, the whole premise would collapse. Everything runs locally by design.

Why encrypt saved exports? The filter has to read plain text while it is checking the transcript. That part happens in memory. Saved files are different. They can include the redaction map, which may contain the exact email address, SSN or account number that was removed from the safe transcript. Browser exports use the Web Crypto API to save encrypted JSON. The Python CLI uses AES-256-GCM through the cryptography package, installed with pip install "voicesafekit[crypto]". TLS/HTTPS is still useful when data travels over a network, but it does not encrypt a file sitting on disk.

How the export encryption was built. The analysis engine was left unchanged: it still produces the same structured result with decision, findings, safe_transcript and redaction_map. The encryption layer sits after analysis, at the moment a user chooses to save the result. That keeps detection simple while making the saved artifact safer.

In the browser, the Export JSON button requires a local export key, derives an AES-GCM key through Web Crypto and saves only the encrypted bundle. In the CLI, --out writes encrypted files by default using VOICESAFEKIT_EXPORT_KEY. The explicit --plain-out option is kept for local debugging, and voicesafekit decrypt restores an encrypted export when the same passphrase is available. Tests cover the round trip and confirm that sensitive redaction-map values are not visible in the stored JSON.

07 - Limitations

What it does not do well

English only. The number words, ordinals, months and joiner words in the normaliser are English. "Quatre deux quatre deux" passes through untouched.

Real STT punctuation still breaks some numbers. On the real Whisper transcripts, 7 of 108 PII utterances leaked. Whisper split digit groups with commas, glued a keyword to the number, wrote digits as decimals or misheard the keyword. Section 16 lists the patterns.

Accent and noise sensitivity. Whisper tiny is accurate for clear English speech in a quiet environment. Heavy accents, background noise, or fast speech can produce transcription errors. Those errors may cause sensitive content to be missed. The base model would improve accuracy but at the cost of speed.

Keyword rules miss novel phrasing. The detection rules use fixed patterns and keywords. Someone saying "give me a new dose" rather than "change my medication" would not trigger the medical rule. A neural classifier trained on intent would handle this better.

Text only, not audio. VoiceSafeKit cleans the transcript. If the audio itself is recorded, the card number is still in the recording. Bleeping or muting those spans is planned but not built.

No streaming input guard. Each final transcript is checked on its own. If the STT splits a card number across two final chunks, neither chunk may look like a card. The browser app also records a full clip before transcribing rather than streaming word by word.

Not a security product. VoiceSafeKit is a fast first layer, not a full privacy programme or a compliance certification. It should not be the sole privacy control in a production voice assistant. Pair it with your own review for PCI DSS, HIPAA or GDPR work.

08 - Future Work

Where this goes next

Earlier versions of this paper named framework integration as the most natural next step. Version 0.5 ships it: an OpenVoiceOS adapter (protect_utterance) that checks STT output before the intent parser, and drop-in processors for Pipecat and LiveKit Agents (section 15). What is still open:

Whisper punctuation in numbers. Found by the ASR benchmark: join comma-separated digit groups after a sensitive keyword, split keywords glued to digits (SSN609507896), handle digits Whisper writes as decimals, and common mishearings ("fin" for PIN). This is the next release.

Audio redaction. Map findings to STT word timestamps and bleep or mute those spans in recordings, plus a PCI "pause recording" signal.

Streaming input guard. Hold back interim transcripts that end in an unfinished number, so a card split across STT chunks is still caught.

Home Assistant and the Wyoming protocol. Wyoming is the lightweight protocol Home Assistant uses between voice satellites and processing servers. A Wyoming proxy that redacts Transcript events, and a redacting conversation agent that wraps any cloud LLM agent, would bring the filter to any Home Assistant voice setup.

Multilingual spoken numbers (French, German, Spanish, Arabic), spelled-out letters and the NATO alphabet ("a for alpha"), spoken postcodes, gateway plugins for LiteLLM and Open WebUI, a LiveKit Redactor backend, and an MCP server so desktop assistants can redact before sending.

09 - Confidence Scoring

Why every finding needs a probability

The original engine returned binary findings: a pattern either matched or it did not. That approach overstates certainty. A phone number matched near a credit card number is less likely to be a real phone number than one found in isolation. A medical keyword in a clearly technical context is less alarming than the same keyword in an emotionally charged message. Binary matching discards this context entirely.

Version 0.2.0 added a confidence: float field to every Finding. Each rule declares a base confidence that reflects how precise its pattern is. Context-aware validators then adjust it: a Luhn-valid card gains 4 percentage points, a phone number written with a leading + gains 8.

Confidence-weighted scoring

The risk score is computed as:

engine.py - confidence-weighted score 
def _score(findings: list[Finding]) -> int:
    total = sum(SEVERITY_POINTS[f.severity] * f.confidence for f in findings)
    return min(100, round(total))

A 70%-confidence high-severity finding contributes 25 points (36 × 0.70) rather than the full 36. A Luhn-verified payment card at 99% confidence contributes 35.6 points. This means the score reflects genuine risk rather than a count of regex matches.

10 - Multi-Turn Conversation Analysis

Why a single transcript is not enough

Voice assistants do not work in isolated utterances. A user might give their name in the first turn, their email address in the second and their date of birth to confirm their identity in the third. Analyzed individually, turns two and three each get a medium-severity result. Seen together, the session reveals a structured identity disclosure that carries much higher real-world risk.

The analyze_conversation function takes an ordered list of utterances and returns a ConversationResult with per-turn analysis, a peak decision, a cumulative score (the highest single-turn score) and the union of all entity kinds detected across the session.

Python - multi-turn analysis 
from voicesafekit import analyze_conversation

result = analyze_conversation([
    "Set a timer for ten minutes.",
    "My SSN is 471-55-8843 - please verify me.",
    "Thank you, that is all.",
])

result.peak_decision    # "BLOCK"
result.cumulative_score # 52
result.seen_kinds       # ("ssn",)
len(result.turns)        # 3

The score is 52, below the REVIEW threshold, yet the decision is BLOCK: a single critical finding (55 points × 95% confidence) is enough. The web app exposes this as a Conversation mode toggle. Each turn is added explicitly, a turn history panel tracks the sequence and a timeline view below the main panels shows every turn's findings and decision alongside a cumulative summary bar.

Design note

analyze_conversation still scores each turn in isolation; it does not yet raise the risk when a name, an email and a date of birth arrive in separate turns. Cross-turn linking is now partly addressed by PrivacySession (section 14): the same value gets the same placeholder in every turn, so the model sees one consistent [CARD_1] and the user can say "use that card again" without the number ever reaching it. Cross-turn risk aggregation remains the most important engineering gap.

11 - New Detector Classes (June 2026)

Financial identifiers, context signals and human vulnerability

The v0.2.0 detector set added three categories that were entirely absent from the original engine.

Financial identity numbers

SSNs, IBANs and CVV codes are the three most common financial identifiers that a voice assistant user might accidentally speak. Each has a distinct detection challenge.

SSN - The pattern \b(?!000|666|9\d{2})\d{3}[-\s]\d{2}[-\s]\d{4}\b excludes area numbers that the Social Security Administration has never issued. This eliminates a class of false positives from account numbers and tracking codes that happen to match the XXX-XX-XXXX format. People rarely say the dashes, so version 0.5 adds a second rule: nine digits with optional separators, but only right after "social", "social security" or "SSN".

IBAN - The pattern matches the standard two-letter country code, two check digits and 11-30 alphanumeric BBAN characters. A mod-97 checksum then validates the matched text. Without this step, any sufficiently long alphanumeric string near a country code would be flagged.

CVV - Unlike card numbers, CVV codes are short (3-4 digits) and indistinguishable from any other number without context. The detector is keyword-triggered: it only fires when a CVV/CVC/security-code phrase precedes the number.

Emotional and situational context

Two intent categories address situations that no PII detector can catch but that require fundamentally different assistant behavior.

The emotional distress signal fires on phrases expressing hopelessness, worthlessness, or a desire to disappear. When detected, the assistant guidance changes: instead of "redact and proceed," the guidance tells the assistant to respond with empathy and direct the user to appropriate support. The confidence is set at 70% because emotional language is genuinely ambiguous - "I feel like giving up" can mean quitting a project as easily as it can signal a crisis.

The coercion signal fires on phrases suggesting the user is being directed by a third party: "they made me say this," "don't tell anyone I said this." This is the lowest-confidence detector in the system (65%) because coercive language and ordinary reporting language overlap substantially. A higher false negative rate is acceptable here because the guidance produced is non-destructive - it simply tells the assistant not to act on instructions that may have been forced.

12 - Spoken-Form Normalisation

Reading speech the way STT writes it

voicesafekit/spoken.py rewrites spoken numbers, emails and dates into written form before any rule runs. It is pure Python, about 360 lines, and has no model behind it. The hard part is not turning "four" into 4. It is knowing when not to: "two kids", "oh I see" and "meet me at home" have to come out untouched, or the filter would bury every transcript in false alarms.

→
tokens
→
"4242424242424242"
→
card rule + Luhn
→
span map
→

How it works

Step 1

Tokenise

Split into words, digit runs and single punctuation marks, each with its character offsets.

Number runs

Digits as words

"one" to "nine", plus zero, oh, nought and nil. Written digits can mix in: "four two 42".

Number runs

Double and triple

"double oh" becomes 00, "triple five" becomes 555 ("treble" too).

Number runs

Tens, teens, hundred

"forty two" is 42, "forty-two" too, "nineteen ninety" is 1990, "nine hundred" is 900.

Number runs

"plus" and separators

"plus four four …" becomes +44. Commas, dashes and dots between number words stay inside the run.

Guard

Weak "oh"

"Oh" and "o" only count as zero when another number word is next to them. "Oh I see" is left alone.

Guard

Words and 3+ digits

A run is rewritten only if it contains number words and produces at least 3 digits. "Two kids" is untouched.

Guard

Spoken emails

"Dot", "at", "underscore", "dash". Needs a spoken joiner and a known TLD, so "meet me at home" never matches.

Guard

Date ordinals

"March fourth" becomes "march 4th", "twenty first of may" becomes "21st of may", only next to a month.

Mapping back to the original words

The normaliser returns a NormalizedText: the written text plus, for every character in it, the span of the original transcript it came from. Every rule runs on the written text. Each finding's span is then passed through to_original(start, end), so the redaction is applied to the words the user actually said. The 11 characters of 07700900123 map back to all 53 characters of "oh seven seven double oh nine double oh one two three", and the safe transcript reads "call me on [phone removed]" with nothing left over.

Each finding also carries a spoken flag, set when the written text of the match differs from the original slice. It tells you which findings a text-only filter would have missed, and it adds a line to the assistant guidance: treat spoken details exactly like written ones.

Python - spoken-form normalisation 
from voicesafekit import analyze_transcript, normalize_spoken

norm = normalize_spoken("call me on oh seven seven double oh nine double oh one two three")
norm.text                  # 'call me on 07700900123'
norm.to_original(11, 22)   # (11, 64): 'oh seven seven double oh nine double oh one two three'

result = analyze_transcript("my social is four seven one, five five, eight eight four three")
result.decision            # 'BLOCK'
result.safe_transcript     # 'my social is [SSN removed]'
result.findings[0].spoken  # True

analyze_transcript("my social is four seven one, five five, eight eight four three",
                   spoken=False).decision                 # 'SAFE'
analyze_transcript("I have two kids and we leave at five").decision  # 'SAFE'
Turning it off

Normalisation is on by default everywhere. spoken=False in Python, --no-spoken on the CLI and the spoken-mode toggle in the browser app switch it off, which is also how the "spoken mode off" baseline in section 16 is produced.

13 - False Positives Fixed

A filter that cries wolf gets switched off

A privacy filter that blocks "how much should I keep in my emergency fund?" teaches developers to ignore it. Building the SpokenPII benchmark meant writing 40 ordinary requests designed to look risky, and the 0.4 engine tripped on several of them. Each was fixed with the narrowest rule change that kept the real case working. All of the outputs below come from running the 0.4 and 0.5 engines on the same sentence.

Sentence0.40.5Fix

Tightening the secret rule did not make it weaker. "My password for netflix is hunter22" was missed by 0.4 because of the words between "password" and "is". The 0.5 rule allows up to two "for/to/on [my] X" phrases there and now returns "my [secret removed]".

The lazy card regex

One fix was a real leak rather than a false alarm. The old card pattern used a lazy separator, so once it had 13 digits it was allowed to stop at the next space. On a number with a trailing group, it redacted the start and left the end readable:

rules.py - payment card pattern 
# 0.4: lazy separator, the match may end at any space after 13 digits
\b(?:\d[ -]*?){13,19}\b
#   "my card is 4000 0566 5566 5556 123" -> "my card is [payment number removed] 123"

# 0.5: at most one separator between digits, and the match must end on a digit
\b(?:\d[ -]?){12,18}\d\b
#   "my card is 4000 0566 5566 5556 123" -> "my card is [payment number removed]"

14 - Reversible Placeholders

Redact for the model, restore for the voice

Plain redaction breaks voice agents. If the model only ever sees "[email removed]", it cannot say "I've sent the receipt to your email at alex dot rivera at gmail dot com", and the user has no way to check it heard them right. PrivacySession keeps both goals: the model sees numbered placeholders, the user hears their real values, and the mapping between them lives only in memory.

Before the LLM

protect(text)

Swaps personal data for [EMAIL_1], [CARD_1], [NAME_1] and returns the decision and findings.

After the LLM

restore(text)

Puts the real values back into the reply. Unknown placeholders are left as they are.

Token streams

stream()

Holds back a partial placeholder such as "[EMA" until the next chunk completes it.

Stored context

reprotect(text)

Swaps restored values back to placeholders before a reply is saved to the chat history.

The same value gets the same placeholder for the whole session. Values are keyed by kind and a canonical form: the normalised, lower-cased value with spaces, dots, dashes and brackets removed. "alex dot rivera at gmail dot com" in turn one and "alex.rivera@gmail.com" in turn two are both [EMAIL_1], so the model can follow the conversation without ever seeing the address.

Credentials are never stored. Passwords, PINs, CVVs, one-time codes and API keys still get placeholders, but their values are not kept in the map, so the model cannot get the voice to read them back, by accident or by prompt injection. (A session has to be created with restore_credentials=True to change that.)

Intents stay in the text but are reported. Medical, legal, financial, distress, coercion and emergency findings are not replaced, because the model needs to know the user has chest pain to answer well. They still set the decision, and protected.blocked says whether the turn should be forwarded at all.

Python - PrivacySession 
from voicesafekit import PrivacySession

session = PrivacySession()

session.protect("email me at alex dot rivera at gmail dot com").text
# 'email me at [EMAIL_1]'
session.protect("actually use alex.rivera@gmail.com and my pin is 4821").text
# 'actually use [EMAIL_1] and my pin is [PIN_1]'

session.restore("Done, I've emailed [EMAIL_1]. Your PIN [PIN_1] is not stored.")
# "Done, I've emailed alex dot rivera at gmail dot com. Your PIN [PIN_1] is not stored."
session.mapping
# {'[EMAIL_1]': 'alex dot rivera at gmail dot com'}    no PIN in memory, ever

stream = session.stream()
stream.feed("Sent to [EMA")       # 'Sent to '  (partial placeholder held back)
stream.feed("IL_1] just now.")    # 'alex dot rivera at gmail dot com just now.'
stream.flush()                    # ''

session.reprotect("I've emailed alex dot rivera at gmail dot com.")
# "I've emailed [EMAIL_1]."

turn = session.protect("I have chest pain, my email is sam@example.com")
turn.text       # 'I have chest pain, my email is [EMAIL_2]'
turn.decision   # 'REVIEW'  (the medical intent stays in the text and is reported)

The restored value is the form the user first used. Because the first mention was spoken, the TTS voice says "alex dot rivera at gmail dot com" rather than trying to pronounce an @ sign.

15 - Voice Framework Integrations

Drop-in processors for Pipecat and LiveKit

A filter is only useful where the transcript actually flows. Most production voice agents are built on a framework that wires STT, LLM and TTS together, so version 0.5 ships processors for the two most widely used open-source ones. Both share a single PrivacySession per conversation, so the input side and the output side agree on what [CARD_1] means.

Pipecat

voicesafe_processors() returns three frame processors that sit at three points in the pipeline:

The input processor goes after STT and before the user aggregator. It protects every final TranscriptionFrame before the LLM sees it, and interim transcriptions too, because they reach UIs and logs. It fires an on_decision event for every final transcript and on_block when one is blocked. A blocked transcript is dropped by default and a short refusal is spoken instead, pointing to the local emergency number.

The output restorer goes between the LLM and TTS. It runs the streamed LLMTextFrame tokens through a stream restorer, starting a fresh one for each response and flushing it at the end, so the voice says the real values.

The context guard goes before the assistant aggregator. It swaps restored values back to placeholders, so the stored assistant reply, which the LLM will read on the next turn, never contains them.

Python - Pipecat pipeline 
from voicesafekit.integrations.pipecat import voicesafe_processors

guard_in, restore_out, guard_context = voicesafe_processors()

pipeline = Pipeline([
    transport.input(), stt,
    guard_in,             # spoken PII -> [CARD_1], [EMAIL_1] before the LLM
    user_aggregator, llm,
    restore_out,          # real values back for the voice only
    tts, transport.output(),
    guard_context,        # stored assistant replies keep the placeholders
    assistant_aggregator,
])

@guard_in.event_handler("on_block")
async def on_block(processor, protected):
    ...  # emergencies, government IDs, CVVs: never forwarded, refusal is spoken

The offline demo runs this pipeline with a fake STT frame and a fake LLM that streams its reply in awkward chunks ("Thanks [NA", "ME_1]. …"), so it needs no API keys. Its output, verbatim:

examples/pipecat/offline_demo.py - output 
User says    : Hi, my name is Alex Rivera. My card number is four two four two four two four two four two four two four two four two and my email is alex dot rivera at gmail dot com.
LLM receives : Hi, my name is [NAME_1]. My card number is [CARD_1] and my email is [EMAIL_1].
TTS says     : Thanks Alex Rivera. I'll send the receipt to alex dot rivera at gmail dot com.

LiveKit Agents

VoiceSafeAgent is a subclass of LiveKit's Agent. It overrides two hooks. on_user_turn_completed protects the user's message before the LLM sees it; if the turn is blocked it says the refusal (without adding it to the chat context) and raises StopResponse, so the LLM is never called. tts_node restores placeholders in the streamed reply before passing it to the default TTS node, so the voice says the real values while the chat context and on-screen transcript keep the placeholders.

Python - LiveKit agent 
from voicesafekit.integrations.livekit import VoiceSafeAgent

class Assistant(VoiceSafeAgent):          # instead of Agent
    def __init__(self):
        super().__init__(instructions="You are a helpful voice assistant.")

For transcript and log hooks, VoiceSafeRedactor().redact(text) is stateless and idempotent: running it twice gives the same output, which matters for hooks that may see the same text more than once.

Tested versions

Tested against Pipecat 1.15 and LiveKit Agents 1.8, and a separate CI job runs the integration tests. Install with pip install "voicesafekit[pipecat]" or "voicesafekit[livekit]"; the core package never imports either framework.

16 - The SpokenPII Benchmark

Measuring PII as speech-to-text writes it

No public benchmark measures PII in the form speech-to-text produces, so the repository ships one in two parts. Both compare VoiceSafeKit 0.5, the same engine with spoken mode off, and Microsoft Presidio 2.2 with spaCy's en_core_web_lg model.

SpokenPII (synthetic). 580 labelled sentences: 270 with PII written normally, the same 270 values written the way they are spoken, and 40 tricky requests with no PII at all ("emergency fund", "call Sue", "twenty five minutes"). A gold span counts as protected only if at least 90% of its non-space characters are redacted. A no-PII sentence counts as a false alarm if anything in it was redacted.

SpokenPII-ASR (real speech-to-text). 148 of the spoken scripts, 108 with PII and 40 without, were read aloud by the macOS voice Samantha, digit by digit the way people say them, and transcribed by faster-whisper base.en on CPU. Here exact spans no longer line up, so the test is stricter in a different way: a sample leaks if the value can still be recovered from the redacted transcript after spoken-form normalisation. Whisper base.en wrote 92 of the 108 PII utterances fully in digits and symbols. So on this engine, the gap between VoiceSafeKit and Presidio comes as much from false alarms and voice-specific rules (PINs, one-time codes, spoken emails) as from spoken numbers. Engines and settings that write more of the speech as words will look more like the synthetic set.

Read these numbers honestly

The same author wrote the synthetic set and the detector, so 100% there mostly shows that the templates are covered. Treat it as a regression suite. The ASR set is the fairer test: these are first-run numbers and nothing was tuned on it. Presidio is a general-purpose tool run with its defaults, not configured for speech; its false alarms are mostly DATE_TIME and PERSON hits on ordinary requests.

How real STT broke it: the 7 misses

The 7 ASR leaks are the most useful result in the benchmark, because they show failure modes no synthetic template would have predicted. They fall into four patterns, and fixing them is the next piece of work (issue #6):

Miss

Comma-split groups

Whisper punctuates digit groups like a list: 3790, 4339, 7110, 7181. No single group is long enough to be a card.

Miss

Keyword glued to digits

SSN609507896: no word boundary between the keyword and the number, so the SSN rule never starts.

Miss

Digits as decimals

073, 49.95, 3022: part of the number becomes a price.

Miss

Misheard keyword

my fin is 96-28: "PIN" heard as "fin", so the keyword-triggered rule has nothing to anchor on.

Everything is reproducible from the repository:

Shell - reproduce the benchmark 
python benchmarks/run.py --presidio          # synthetic SpokenPII
python benchmarks/asr.py score --presidio    # SpokenPII-ASR

The most valuable contribution anyone can make is a transcript from their own STT engine (Deepgram, Vosk, Parakeet, Moonshine or a cloud API) that VoiceSafeKit missed, with fake data only. The repository has an issue template for exactly that.

17 - Closing

What this project is really about

Voice assistants are getting smarter quickly. The gap between what someone says and what an AI model is allowed to act on needs careful thought. Most of the safety work in this space focuses on model outputs (preventing harmful responses) rather than model inputs (preventing harmful data going in).

VoiceSafeKit is an argument that input filtering matters too, that for voice it has to read speech the way speech-to-text writes it, and that it can be done locally, in well under a millisecond, with no infrastructure and no dependencies. The code is open-source. The approach is intentionally simple so that it can be understood, copied and improved, and the benchmark is there so that "improved" can be measured.

Try it

The live application is at mohamadkanso.github.io/VoiceSafeKit: say a card number out loud and watch it disappear. The full source, the benchmark and the Pipecat and LiveKit examples are on GitHub, and the library installs with pip install git+https://github.com/MohamadKanso/VoiceSafeKit.
